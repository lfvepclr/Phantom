# 路由器内核分流（ipset+fwmark）：直连回到内核快路径 + 夜间性能取证

日期：2026-10-04
范围：`client/src`（gateway / ipset / tun / stats / whitelist / tunnel）、`client/cli`（`--gateway-mode`）、
`client/koolshare`（插件控制面 + ASP + 冒烟测试）、`xtask rules update` 与 `client/data` 白名单数据；**服务端不改**。
目标机：ASUS RT-AX86U Pro（BCM4912，固件 `3.0.0.4.388_24199_koolcenter`），`<路由器IP>`，koolshare 软件中心插件形态。

## 目标

"晚上人多时，非 VPN 的网站/视频也慢"。要求先定位再优化，目标是接近无感，且**不影响 VPN**
（被墙站点照常走隧道）。同时先回答"非 VPN 流量是不是被加解密拖慢的"，避免改错地方。

## 结论（实施记录）

### 根因

| 编号 | 缺陷 | 证据 |
|---|---|---|
| R1 | **所有** LAN 转发流量（含直连）都被 `ip rule iif br0 lookup 200` 灌进 TUN，由用户态 TCP 栈逐连接终结并重发；Broadcom 硬件加速完全用不上 | LAN 4 路并行直连仅 **14.2 MB/s（114 Mbps）**，而路由器本机内核路径 8 路并行有 **420 Mbps**；`/proc/fcache/nflist` 125 条流 `HW_Hits` 全 0；插件计数 17593 条连接里 15263 条是 direct —— 这些"直连"全在用户态被中转 |
| R2 | "直连被加解密"**不成立** | 直连走 `RuleAction::Direct → spawn_direct_tcp_flow → tcp_direct_relay_task → TcpStream::connect`（明文，不进服务端）；只有 `Proxy` 分支进 AEAD。直连实测 114+ Mbps，远超服务端 3 Mbps 上行上限，被加密早就被卡死 |
| R3 | 夜间高并发的三个隐患：fd 软上限只有 1024；日志默认 `info` 且无人裁剪（实测已涨到 28,614 行）；页面 CPU 恒为 0 | `/proc/<pid>/limits`（1024/4096）、`wc -l /tmp/upload/phantom_log.txt`、busybox `ps` 无 `-o` 导致指标恒 0 |
| R4 | 内核分流上线后 **DNS 全超时、网页打不开**，但进程/路由/ipset 全正常 | 本固件**没有 `sysctl` 二进制**，原来的 `sysctl -w net.ipv4.conf.<tun>.rp_filter=0` 一直静默失败；TUN 注入的回包源是公网 IP，被严格反向路径校验丢弃（`FORWARD -i phantom0 -o br0` 计数为 0，`phantom0 rp_filter=1`） |

### 改动

- **内核分流**（`--gateway-mode kernel-split`，默认）：`ipset phantom_proxy`（hash:net）+
  `iptables -t mangle PREROUTING … -m set --match-set … -j MARK 0x1` + `ip rule fwmark 0x1 lookup 200`，
  只把**白名单目标**与 DNS(53) 送进 TUN；**移除**通配 `iif br0 lookup 200`。
  缺 `ipset`/`xt_set` 时自动回退 `relay`（原行为），页面也可手动切换。
- **白名单 IP 三个来源**：① DNS 实时学习（隧道解析白名单域名 → A 记录 1s 合并 `ipset restore`，
  30 min 超时）；② 内置 CIDR（Telegram 12 段 + **Google 官方 `goog.json` 130 段**，`timeout 0` 永久，
  覆盖 YouTube/googlevideo，由 `cargo xtask rules update` 刷新）；③ 加密 DNS 拦截（DoT/DoH，默认开、可关）。
- **rp_filter**：改为直写 `/proc/sys/net/ipv4/conf/{<tun>,all}/rp_filter`（`0` / `2`，内核按
  `max(all,iface)` 判定），启动后回读校验，仍为 strict 时打 WARN。
- **数据面其他**：未知非 SYN 流回 RST（动态标记下应用立刻重连，不再静默黑洞）；新增指标
  `phantom_direct_bytes_*` / `phantom_tunnel_bytes_*` / `phantom_whitelist_ipset_entries` /
  `phantom_gateway_kernel_split` / `phantom_tun_unknown_flow_rst_total`。
- **插件控制面**：新增 dbus `phantom_gateway_mode`、`phantom_block_doh` 与页面对应控件；
  状态卡新增"分流模式 / 白名单条目 / fd 使用"；启动前 `ulimit -n 16384`；日志默认 `warn`、
  看门狗每 5 分钟调 `_trim` 裁剪；CPU 指标改读 `/proc/<pid>/stat`；新增夜间采样器
  `phantom_perf.sh`（cru 每 5 分钟）与 `diag` 段落；卸载清理 ipset / mangle / fwmark / DoH 规则。
- **白名单数据**：`cargo xtask rules update` 合并 Google 官方网段；`rules verify` 增加
  YouTube 常用段（`142.250/172.217/74.125/173.194/216.58.192`）与 Telegram 段断言。

### 验证

- 单测：`cargo test -p phantom-client --lib` **90 passed**（双模式规则集、ipset 批量与 TTL、
  种子永久性、未知流 RST、直连/隧道分段计数）。
- 编译：干净 HEAD worktree 内 `cargo check --workspace --all-targets` 通过。
- 冒烟：koolshare 模式 **119/119**、`/jffs` 降级模式 **119/119**（含软件中心回包契约、fd 上限、
  采样落盘、卸载清理 ipset 的断言）。
- 真机 A/B（同机同时段）：

  | 项目 | 兼容模式（relay） | 内核分流（kernel-split） |
  |---|---|---|
  | LAN 直连 4 路并行聚合 | 14.2 MB/s ≈ 114 Mbps | **48–50 MB/s ≈ 390 Mbps（3.4×）** |
  | 同负载 phantom CPU（`top`） | 27–31%（约 1.2 核） | **0.0–0.1%** |
  | 直连路径 | 全部进 TUN、用户态中继 | 不进 TUN（`direct_bytes` 恒 0 即证据） |
  | 隧道内站点 | 正常 | 正常（youtube 200 / google 204，日志 `-> Proxy (whitelist)`） |
  | ipset | 无 | 138（种子）→ 174（DNS 学习累计，随浏览增长） |

- 容错与回退：`relay ⇄ kernel-split` 页面/dbus 各切一次，规则与 ipset 正确建立与清理；
  抹掉 mangle + fwmark 后 `ks-nat-start.sh start_nat` 自动补回；rp_filter 修复后 DNS、
  直连与隧道路径全部恢复。
- 部署：`cargo xtask package koolshare` 产出 `dist/phantom-0.1.0.tar.gz`
  （sha256 `e8c0953d…`，双架构 aarch64 + armv7，`.valid=hnd`）；**已在路由器软件中心安装并启用**，
  装后设备文件与源码一致（UI r5、ASP md5 相同、脚本与二进制哈希相同），运行态
  `gw:"kernel-split"`、ipset 174 条、fd 23/16384、DoH 拦截 16 条、采样器持续在写。

### 明确不做

- **不预热**内置 4.4k 域名（按用户选择）：YouTube 由 Google 官方 CIDR + DNS 实时学习覆盖。
- **不改服务端**：本轮无服务端代码变更，服务端无需重新部署。
- **不做硬件 offload 适配**：`fc_hw` 仍为 0，但直连已回到内核软件路径（390 Mbps、系统 CPU ~7%）。
- armv7 机型、ROG/TUF 皮肤、路由器重启自启：留到有条件时验证。

## 遗留

- **过夜采样对比**：`/tmp/upload/phantom_perf.log` 每 5 分钟一行，跑满一个晚高峰后回看
  `cpu_pct / fc_hw / fd / rtt_ms / loss_pct / wifi / link`，确认瓶颈是否已转移到 ISP 晚高峰或 WiFi 空口。
- `eth2` 口协商为 100 Mb/s（eth0 为 1000 Mb/s）：确认哪台设备接在 eth2。
- `fc_hw=0`：确认 mangle 标记是否阻止了 Broadcom Runner 命中直连流。
