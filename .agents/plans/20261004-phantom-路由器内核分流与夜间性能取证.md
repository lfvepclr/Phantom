# Phantom 路由器形态：内核分流（ipset+fwmark）与夜间性能取证

- 计划日期：2026-10-04
- 目标机器：`<路由器IP>`（RT-AX86U Pro，`3.0.0.4.388_24199_koolcenter`，SSH <SSH端口>）
- 关联：[client/koolshare/README.md](../../client/koolshare/README.md) §7.0、[tests/PERF_ROUTER_REPORT.md](../../tests/PERF_ROUTER_REPORT.md) §4.1

## 1. 问题

"晚上人多时，非 VPN 的网站/视频也慢"。实测证据（同一台机器）：

| 路径 | 实测 | 说明 |
|---|---|---|
| 路由器本机 8 路并行（内核路径） | 420 Mbps | 硬件/内核能力 |
| LAN 经插件 4 路并行（全部进 TUN） | 114–140 Mbps，phantom CPU 27–31% | 用户态 relay 封顶 |
| `/proc/fcache/nflist` | 125 条流 `HW_Hits` 全 0 | 硬件加速完全没用上 |
| 插件计数 | 17593 条连接里 15263 条是 direct | 88% 的"直连"也在用户态被中转 |

**已证伪"直连被加解密"**：直连走 `RuleAction::Direct → tcp_direct_relay_task →
TcpStream::connect`（明文），只有 `Proxy` 进隧道；唯一例外是"直连失败回退隧道"（实测
0.3%）。直连能跑到 114+ Mbps 也远超服务端 3 Mbps 上行上限 —— 若被加密早就被卡死。

## 2. 方案

**只把白名单目标送进 TUN，其余留在内核快路径**（`--gateway-mode kernel-split`，默认）：

- ipset `phantom_proxy`（hash:net, timeout 1800）+ `iptables -t mangle PREROUTING … -m set
  --match-set … -j MARK 0x1` + `ip rule fwmark 0x1 lookup 200`；额外标记 53 端口保证 DNS
  仍进隧道（域名学习的前提）；移除通配 `iif br0 lookup 200`。
- 白名单 IP 来源：① DNS 实时学习（隧道解析白名单域名→A 记录批量 `ipset restore`）；
  ② 内置 CIDR（Telegram 12 段 + **Google 官方 goog.json 130 段**，覆盖 YouTube/googlevideo，
  由 `cargo xtask rules update` 刷新）；③ 加密 DNS 拦截（DoH/DoT，默认开，可关）。
- 缺 `ipset`/`xt_set` 自动回退 `relay`（原行为）；页面可手动切换。
- 配套：fd 上限 16384（原软上限 1024）、日志默认 `warn` + 看门狗每 5 分钟裁剪、
  CPU 指标改读 `/proc/<pid>/stat`（busybox 无 `ps -o`）、新增 `phantom_perf.sh` 夜间采样、
  直连/隧道分段字节计数、未知非 SYN 流回 RST。

## 3. 实施结果（同日真机验收）

| 项目 | 前（relay） | 后（kernel-split） |
|---|---|---|
| LAN 直连 4 路并行聚合 | 14.2 MB/s ≈ 114 Mbps | **48–50 MB/s ≈ 390 Mbps（3.4×）** |
| 同负载 phantom CPU | 27–31% | **0.0–0.1%** |
| 隧道内站点 | 正常 | 正常（youtube 200 / google 204，`-> Proxy (whitelist)`） |
| ipset | 无 | 138（种子）→ 156（浏览后） |
| fd 上限 | 1024 | 16384（实测生效） |
| nat-start 重放 | 规则补回 | 规则补回（fwmark + 3 条 MARK + ipset） |

### 3.1 实施中发现的坑（务必保留在文档里）

1. **本固件没有 `sysctl` 二进制**：原来的 `sysctl -w net.ipv4.conf.<tun>.rp_filter=0`
   一直静默失败。内核分流上线后表现为"DNS 全超时、网页打不开，但进程/路由/ipset 全正常"。
   根因是 TUN 注入的回包源地址是公网 IP，严格 rp_filter 直接丢弃。修复：直写
   `/proc/sys/net/ipv4/conf/{<tun>,all}/rp_filter`（`all=2`，内核按 `max(all, iface)` 判定），
   启动后回读校验并在仍为 strict 时 WARN。
2. **测试 mock 的 `grep -v … && mv` 陷阱**：删掉最后一行时 `grep -v` 返回 1，`mv` 不执行，
   规则还在、下一次删除又"成功" → 调用方的 `while iptables -D …` 死循环。mock 里已改为
   先重定向再 `mv`，并写进注释。
3. **`proc_cpu_ticks` 代替 `ps -o pcpu`**：页面 CPU 之前恒为 0，夜间问题没有数据可查。
