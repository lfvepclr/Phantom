# 鸿蒙 YouTube 卡顿：先测后修 + 跨端不回归

## 摘要

真机数据已定位到两个客户端数据面缺陷（均在共享的 TUN 路径里，不在服务端、不在分流规则）：YouTube 视频 CDN 流（`r4---sn-ogueln66.googlevideo.com` → 142.251.91.201:443，走隧道）在 7 秒内产生 **1600 次「3-dup-ACK 整窗重传」**，向 `vpn-tun` 写入 115 MB 几乎全为重复数据，期间只有 0.45 MB 有效下行、内核丢 58,814 个上行包（`txqueuelen 500` 溢出）。对照：同一时段 Mac SOCKS5 隧道实测 **333 KB/s / 15.3 MB**，裸链路 310–362 KB/s（VPS 上行 ~3 Mbps 是硬上限）。

本轮按「先检测 → 再修 → 复测」推进：先补计量与可复现脚本并采一轮基线，再修 (a) 读包持锁导致的写饥饿、(b) dup-ACK 整窗重传自持循环，最后用同一套脚本复测，并以 Mac SOCKS5 + loopback + 单测作为「没让 Mac 变慢」的硬门。

## 阶段 A：先检测（仪器化 + 基线）

- **TUN 计量接入**（`client/src/tun.rs` + `client/src/stats.rs`）：TUN 路径补 `record_tcp_up/down`；下行只计**唯一字节**，重传字节单独计数；UDP 在读包处计 `udp_up`，在直连回包与代理回包两处补 `udp_down`（现在 TUN 模式恒为 0，属统计缺口）。
- **新增计数（累加进 stats JSON）**：`tcp_dup`（重复注入字节）、`dup_acks`（dup-ACK 事件数）、`tun_wq_ms`/`tun_wq_max_ms`（写 TUN 等待可写的时间与峰值）、`tun_txq_peak`（写队列峰值）。鸿蒙 `VpnBridge`/Mac `TrafficSnapshot` 都是按 key 取值、容忍未知键，增键安全。
- **trace 增行**（限速 ≥1 次/秒/流，保持 5000 行上限）：`retransmit <dst> snd_una=… bytes=… dup_acks=… queued=…`；写等待 >100 ms 时 WARN `tun write stalled <ms>ms`。目的是让「卡在哪一层」在手机日志里直接可读。
- **新增两件可复现工具**：`scripts/tun-trace-report.py`（输入拉回的 `phantom_tun_trace.log`，输出每流有效/重复字节、dup-ACK 速率、注入间隔直方图、结束原因，附 PASS/FAIL 判定，支持 `--json`）与 `scripts/harmony-bench.sh`（`hdc file recv` 拉文件 + 每秒采样 `ifconfig vpn-tun` + 应用内 stats + 调用上面的分析器，输出汇总表）。
- **基线采集（改动前，一次，全部用当前 HEAD 重新构建的产物）**：Mac `scripts/speedtest.sh --loopback --rounds 3`、`--uri "<当前 URI>" --origin vps --vps-host root@203.0.113.10 --rounds 3 --check-unblock`；真机用固定工况各 60 s —— ① 播放固定 1080p 视频 `youtube.com/watch?v=aqz-KE-bpKQ`，② 浏览器下载 `https://dl.google.com/go/go1.21.5.linux-amd64.tar.gz`（经 `google.com` 白名单命中隧道），③ 应用内「测速」（SOCKS5 通路，作为同机对照），④ 空闲 60 s。结果写入新文件 `tests/PERF_TUN_PATH_REPORT.md`（含今天已测出的 333 KB/s、310–362 KB/s 锚点，原始 CSV/trace 摘要一并留档）。

## 阶段 B：修复（两个已定位缺陷）

- **F1 读写解耦（`client/src/tun.rs`）**：`TunDevice` 改由单一 pump 任务独占，`select!` 同时处理「读包」与「写队列」；所有写入方（TCP SYN-ACK/ACK/RST/PSH/FIN、UDP 直连与代理回包、DNS 应答）改为投递到写队列，不再 `lock().await` 后 `write_packet`。队列用 `Mutex<VecDeque<Bytes>> + Notify` 非阻塞入队，生产者在队列超过 `4 MiB` 高水位时用 `SEND_HIGH_WATER` 同款背压等待，构造上不可能死锁；顺序按入队顺序保持。写路径进入前 TUN 的 API（`TunProxy::new/run`）不变，平台桥（`platform/{android,macos}.rs`）无需改签名。
- **F2 重传纪律（同文件）**：dup-ACK 快速重传不再整窗回退重发。改为：① 每次只重发 `SND.UNA` 起的 1 个 MSS；② 重传后加冷却（`RETRANSMIT_GUARD = 50 ms`，冷却期内只累计不计事件）；③ 记录「无进展重传轮次」，按 50/100/200/400/800/1600 ms 指数退避，连续 6 轮无进展则发 RST 结束该流让 App 立即重连；④ 每流重复注入预算 `256 KiB/s`（1 s 窗口）与累计 `8 MiB`，超限即 RST——保证单流再也无法像今天那样灌进 100 MB 重复数据；⑤ 与既有 12 拍 stall 丢弃、零窗口探测共用同一套计数，避免两套逻辑互相抵消。
- **明确不在本轮**：不改 `.cargo/config.toml`、不改白名单数据、不改服务端/协议。窗口缩放协商（当前 SYN-ACK 无 wscale，手机窗口被限在 64 KB）留作**触发式后续项**：仅当复测显示 TUN 下行 < SOCKS5 对照的 60% 且 trace 证据为「inflight 长期顶在 64 KB、App 每 2 段不足一次 ACK」时才做。

## 接口与产物变更

- stats JSON 增键 `tcp_dup`、`dup_acks`、`tun_wq_ms`、`tun_wq_max_ms`、`tun_txq_peak`（纯增量；`up/down/udp_up/udp_down` 从此在 TUN 模式才有意义）。鸿蒙详情面板可选展示 `tcp_dup`/`tun_wq_max_ms`，Mac 端不改 UI。
- TUN trace 增 `retransmit …` 与 `tun write stalled …` 两类行，分析器同时兼容旧格式。
- 新增 `scripts/tun-trace-report.py`、`scripts/harmony-bench.sh`；`scripts/speedtest.sh` 增可选 `--out <file>` 追加报告行。
- 新增 `tests/PERF_TUN_PATH_REPORT.md`（改动前后同表对比）与 pump 回归单测。

## 测试与验收

- **单测（防回归，先于真机）**：新增 mock 设备用例——`read_packet` 永不就绪时，连续入队 100 个包必须在 1 s 内全部写出（今天必然失败）；另有「重传限幅 + 退避 + 重复预算触发 RST」用例。`cargo test -p phantom-client --lib`、`-p phantom-e2e`（含 `tcp_session_pool`）全绿。
- **鸿蒙真机（主验收，同一 URI/同一时段窗口）**：60 s 视频播放期间 TUN 平均下行 ≥ 250 KB/s（≥ 333 KB/s 对照的 75%）；60 s `dl.google.com` 下载 ≥ 12 MB；trace 中 dup-ACK 事件 ≤ 5/分钟、重复注入 ≤ 1.2× 有效字节、最大单流有效下行 ≥ 5 MB（今天 73 KB）；测试期间 `vpn-tun` TX dropped 增量为 0；同一视频播放 rebuffer ≤ 1 次（3 Mbps 上限下预期 720p，分辨率不作为失败项）。
- **Mac 不回归（硬门）**：`--loopback` 与 `--uri … --origin vps` 3 轮中位数相对基线下降 ≤ 5%，`--check-unblock` 全绿；今天 spot check 333 KB/s / 310–362 KB/s 即为量级参考。
- **结论落档**：把前后数字写进 `tests/PERF_TUN_PATH_REPORT.md`，并在 `client/harmony/docs/NETWORK_OPTIMIZATION_GUIDE.md` 的复核章节补一小节（缺陷根因、量测方法、验收阈值），避免下次重复踩。

## 假设与默认

- 按你的选择：**路由器本轮不测**。共享的 `client/src/tun.rs` 修复对路由器同源生效，路由器的行为回归由 Mac SOCKS5 + loopback + 单测覆盖，待你开放 `<路由器IP>:22` 后再补真机 A/B。
- 按你的选择：**VPS 上行 310–362 KB/s（~3 Mbps）作为已知硬上限本轮只报告**，不换节点；因此验收阈值按 ≥250 KB/s 设定，1080p60 需更强节点属后续事项。
- 真机测量使用已连接的 HOP-AL00（`<设备UDID>`）；模拟器无 `com.huawei.hmos.vpndialog`，不能建 TUN，只用于 UI 检查。真机工况由人工按脚本提示操作，不做 UI 自动化；每次重启隧道会重置 trace 文件与 `vpn-tun` 计数，测量前统一重启一次。
- 今天的 333 KB/s / 310–362 KB/s / 1600 次重传 / 58,814 丢包属 spot check，正式 A/B 的基线用当前 HEAD 重新构建后重测。
