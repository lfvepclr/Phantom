# 蜂窝 IPv6 泄漏与隧道 AAAA 死循环修复

日期：2026-10-04
范围：共享核心（`client/src/tun.rs`、`dns.rs`、`tunnel.rs`、`platform/*`）+ `core/src/config.rs` + 鸿蒙 `VpnConfig`；服务端不改。
关联：[20261004-弱网卡顿与传输换挡.md](20261004-弱网卡顿与传输换挡.md)（同轮交付，那份记录 W1–W4 弱网/重传/断线问题）。

## 症状

1. 用户报告：鸿蒙端**连 Wi-Fi 开 VPN 正常，用手机网络就不行**。
2. 第一次修复后用户复测：**手机浏览器访问 google.com 根本不成功**，并质疑"怎么验证通过的"。

## 根因（两段，第二段是第一次修复才暴露出来的）

### W5-1：IPv6 从 VPN 漏出去

`VpnConfig` 只声明 IPv4（`10.8.0.2/24` + `0.0.0.0/0`，`isIPv6Accepted` 未开），vpn-tun 上
没有任何 IPv6 地址或路由。于是：

| 观测点 | Wi-Fi（家庭网） | 蜂窝 |
|---|---|---|
| 物理网卡全局 IPv6 | 无（只有 fe80::/ff00::） | `2408:8441:228:f75::/64` |
| vpn-tun 的 IPv6 | 只有 fe80::/ff00:: | 只有 fe80::/ff00:: |
| 结果 | 应用只能建 IPv4 连接，全部被 TUN 接管 | 应用拿到真实 AAAA，按 RFC 6724 优先连 IPv6，**直连物理链路绕过 VPN**，被墙地址被 GFW 黑洞 |

真机证据（修复前，蜂窝，HOP-AL00 / 联通）：

- `/proc/net/tcp6`：2 条 `SYN_SENT → 2404:6800:4005:0827::200e:443`，源地址是运营商地址
  `2408:8441:…`，持续 25 s+ 不消失；
- 应用日志里 `ipv6` 出现 **0** 次 —— 这条连接从未进入隧道；
- 浏览器提示 `No response from this site`。

### W5-2：出口没有 IPv6，App 死磕不可达的 AAAA（第一次修复的错）

第一次修复：把 IPv6 也交给隧道（`fd00:8:8::2/64` + `::/0` + `isIPv6Accepted`），并在
`DnsCache`/`build_dns_response_packet` 里补齐 IPv6 支持。修复后泄漏确实没了 ——
指向被墙地址的连接源地址变成 `fd00:8:8::2`（隧道地址）。

**但 google.com 仍然打不开。** 当时的判断是"服务器没有 IPv6 出口 → 快速 RST → App 回落
IPv4"，并且拿 `Tunnel established` 当成了验收证据。真机日志说明这个判断是错的：

```
route m.youtube.com:53 -> Proxy (dns tunnel) 142.250.199.238   ← IPv4 已到手
route 2404:6800:4005:827::200e:443 -> Proxy (whitelist)        ← 却先连 IPv6
Tunnel failed → [2404:6800:4005:827::200e]:443: Server unreachable
route 2404:6800:4005:827::200e:443 -> Proxy (whitelist)        ← 同一地址重试
Tunnel failed → [2404:6800:4005:827::200e]:443: Server unreachable
```

App **反复重试同一个不可达的 IPv6 地址、从不使用那条 IPv4**，一秒一轮。
所以"把 IPv6 关进隧道"只完成了一半：泄漏是堵住了，但**把出口用不了的地址交给 App**
才是可观察故障的根因。

**教训（写进验收口径）**：`Tunnel established` 只说明传输层通了，不等于页面能打开；
验收必须看**页面加载 / 有效字节数**。第一次修复的报告里已经把这句改成硬规则。

## 方案取舍

| 候选 | 取舍 | 结论 |
|---|---|---|
| A. 依赖 App 自己回落 IPv4（Happy Eyeballs） | 实测鸿蒙浏览器不回落，且不同 App 行为不一致 | **否决**：把正确性交给对方实现 |
| B. 给 VPS 加 IPv6 出口，隧道内真正跑 IPv6 | 要改基础设施，且隧道两端、DNS、relay 都要端到端打通 | **本轮不做**，列为后续（只有服务器真有 IPv6 时才值得） |
| C. 隧道内域名不下发 AAAA（DNS 层拦截） | 一行策略：App 只能拿到 A 记录，隧道本来就只能承载 IPv4；直连域名不受影响 | **采纳**，做成开关、默认关闭 AAAA 转发 |
| D. 全局丢弃 AAAA | 会连带砍掉国内站点的 IPv6 —— 那条路径是真能用的 | **否决** |

| 位置 | 内容 |
|---|---|
| `core/src/config.rs` | 新增 `client.dns_ipv6_via_tunnel`（`#[serde(default)]`，默认 `false`）；默认值与 opt-in 两个单测 |
| `client/src/dns.rs` | `DNS_TYPE_AAAA`；`build_refused_response` 收敛为 `build_status_response(query, rcode)`；新增 `build_nodata_response()`（NOERROR/NODATA，回显 question）；新增 `dns_query_type()`；`DnsProxy` 增 `suppress_tunnel_aaaa` 标志 + setter/getter |
| `client/src/tun.rs` | 新增 `should_suppress_tunnel_aaaa(route, qtype, suppress)`；`handle_dns_query` 在路由判定之后、注册查询之前拦截 AAAA 并直接回包；单测覆盖策略真值表 |
| `client/src/tunnel.rs`、`platform/macos.rs`、`platform/android.rs` | 把配置传进 `DnsProxy`；启动日志追加 `tunnel AAAA = forwarded\|suppressed` |
| 文档 | `ARCHITECTURE.md` §5 配置契约表、`README.md`（TOML 示例 + 热更表）、`client/harmony/README.md`、`NETWORK_OPTIMIZATION_GUIDE.md` §13.8、`tests/PERF_WEAKNET_REPORT.md` |

## 接口与行为契约

- 配置：`client.dns_ipv6_via_tunnel = false|true`（默认 `false`）。
  `false` = 隧道内域名不下发 AAAA；`true` = 需要服务器**确实有 IPv6 出口**时才打开。
- 行为：`Proxy` 路由的 AAAA 查询 → 由劫持直接回 `NOERROR/NODATA`（App 视为"该名字没有
  AAAA"，改用 A 记录）；`Local`（直连）路由的 AAAA 照常转发，A/其它类型一律不受影响。
- 可观测：启动行 `DNS hijack enabled, tunnel resolver = …, direct resolver = …, tunnel AAAA = suppressed`；
  debug 级 `dns AAAA suppressed for tunnel-routed <domain>`。
- 鸿蒙 `VpnConfig` 仍然接管 IPv6（`isIPv6Accepted` + ULA + `::/0`），只是不再把出口不可达
  的地址交给 App；**不改帧格式、不改协议线格式**。

## 剩余 / 后续

- **服务端 IPv6 出口**：本轮 VPS 无 IPv6，隧道内 IPv6 目标只能被快速拒绝；真要 IPv6 出海
  需要给 VPS 加 IPv6，并端到端验证 relay 的 ATYP `0x04` 路径（服务端解析已支持）。
- **弱网台架 A/B**（W1–W4 的量化验收）仍未采集，见 `tests/PERF_WEAKNET_REPORT.md`。
- **窗口缩放（wscale）**：按弱网 trace 的证据触发，条件写在弱网计划里。
- 首次修复的结论与错误判断已在 `tests/PERF_WEAKNET_REPORT.md`、`NETWORK_OPTIMIZATION_GUIDE.md §13.8`
  中原样保留（含"隧道建立 ≠ 页面可打开"这条教训），避免下次重复。
