# 弱网（地铁/蜂窝）卡顿：先测后修 + 传输换挡评估

日期：2026-10-04
范围：共享核心（`client/src`、`core/src/transport`）+ 服务端部署；交付鸿蒙 / Mac / 路由器三端。
关联：[20261004-蜂窝IPv6泄漏与隧道AAAA死循环.md](20261004-蜂窝IPv6泄漏与隧道AAAA死循环.md)
—— 那份是 W5/W5b（IPv6 与隧道 DNS 策略）的完整根因与验证记录。

## 目标

地铁里用蜂窝开 VPN，"特别慢、加载不出来"。要求先检测再优化，并且不能把 Mac / 路由器弄慢。
上一轮定位的 IPv6 泄漏一并修入。

## 结论（实施记录）

### 根因

| 编号 | 缺陷 | 位置 |
|---|---|---|
| W1 | 外层 tunnel socket 静默死亡最长 ~90 s 才被发现（无 `TCP_USER_TIMEOUT`） | `core/src/transport/tcp.rs` |
| W2 | 内层流 6 s 无进展被静默丢弃：不发 RST、不给 relay 停止信号（泄漏） | `client/src/tun.rs` |
| W3 | 鸿蒙侧任何网络能力变化都提升网络 epoch → 所有流 RST | `PhantomVpnExtensionAbility.ets` |
| W4 | 多流复用同一条到 VPS 的 TCP（`pooled session`），一次丢包阻塞全部流 | 传输选型 |
| W5 | VPN 只接管 IPv4，双栈蜂窝下 AAAA 直连物理链路被黑洞 | `VpnConfig` + `dns.rs` |
| W5b | 修 W5 后暴露：出口无 IPv6 时 App 死磕不可达的 AAAA、不回落 IPv4，页面始终打不开 | `tun.rs` + `dns.rs` |

### 改动

- **W5**：`VpnConfig` 增加 `fd00:8:8::2/64` + `::/0` + `isIPv6Accepted`；`DnsCache` 键改
  `IpAddr`；`extract_addr_records()` 同时解析 A/AAAA；`build_dns_response_packet` 支持 IPv6。
- **W5b**（用户复测指出 google.com 仍打不开后补）：隧道内域名（Proxy 路由）的 AAAA 查询
  直接回 `NOERROR/NODATA`（`client.dns_ipv6_via_tunnel`，默认 false），直连域名照常转发；
  `tun.rs::handle_dns_query` + `dns.rs::build_nodata_response()`，配置同步到
  `ARCHITECTURE.md` §5 与 `README.md`。复测：手机 google.com / m.youtube.com 完整加载，
  `tunnel_connect_failures = 0`，`2404:6800` / `Tunnel failed` 出现 0 次。
- **W3**：只认「默认 netId 变化 / 当前默认网络 netLost」，同一网络的能力变化不重置；
  重建 3 s 冷却；日志写 `net change: default A -> B (原因)`。
- **W4**：鸿蒙设置面板加「传输协议 TCP/QUIC」（`phantom_ui.transport`，默认 tcp，重启生效），
  只改写启动请求的 URI；`deploy/alpine/enable-quic.sh` 在 VPS 上并跑 QUIC 实例；客户端日志
  打印 `Connecting to server … (addr, tcp|quic)`。
- **W1**：Linux/Android/OHOS 设 `TCP_USER_TIMEOUT=15s` + 尽力 `TCP_CONGESTION=bbr`；
  macOS 收紧 keepalive 到 30 s/5 s×3；`FailoverManager` 新增 datapath 重置钩子，
  单服务器被判死时清空 TCP/QUIC 池并提升 epoch（只在进入 Down 的那一次触发）。
- **W2**：放弃条件改为「30 s 无 ACK 进展 **且** ≥3 轮重传」，放弃时发 RST、通知 relay 停止、
  计 `flow_stall_drops`；退避上限仍是 4 s。
- **计量**：stats 增 `net_epoch_bumps` / `flow_stall_drops` / `tunnel_connects` /
  `tunnel_connect_failures`；trace 增 `epoch …` / `tunnel connect|closed`，结束原因增 `stall`。
- **工具**：新增 `scripts/weaknet-mac.sh`（pf rdr + NAT + dummynet 台架）；
  `scripts/harmony-bench.sh` 增加外层内核重传（`retrnsmt`）采样；CLI 增加
  `--tun-trace` / `PHANTOM_TUN_TRACE`。

### 方案取舍

| 决策点 | 取舍 | 结论 |
|---|---|---|
| 内层（App ↔ TUN 用户态 TCP 栈）要不要加拥塞控制 | 这段是**无损、RTT≈0 的本机路径**，没有拥塞可测 | 不加；只做"别乱重传、别静默丢流、链路回来能接上" |
| 外层 TCP 用什么算法 | 服务端实测已跑 BBR + fq；BBRv2/v3 未进主线，Copa/PCC 仍在研究阶段 | 客户端**尽力**设 `TCP_CONGESTION=bbr`（失败静默回退），不自研算法 |
| 传输换挡 | `pooled session` 让一条 TCP 承载多条 App 流，一次丢包阻塞全部流 | 加 TCP/QUIC 开关做 A/B；**默认保持 TCP**，由数据决定是否换默认 |
| 窗口缩放（wscale） | 64 KB 窗口在 40 ms RTT 下不是瓶颈（1.6 MB/s ≫ 375 KB/s 链路上限） | **按证据触发**，不默认做；触发条件见下 |
| 抖动处理策略 | 保流优先会让 App 长时间转圈，快速失败会频繁重来 | 混合：真换网/健康检查确认链路已死才重置，普通抖动给 30 s 容忍窗口 |

窗口缩放（wscale）的触发条件（写死，避免"顺手就做"）：同一档位 trace 中某流 `inflight`
连续 ≥200 ms 顶在 App 通告窗口的 ≥95%，且该流有效下行 < 同档 SOCKS5 参照的 60%。

### 接口与可观测

| 位置 | 新增 |
|---|---|
| stats JSON / Prometheus | `net_epoch_bumps`、`flow_stall_drops`、`tunnel_connects`、`tunnel_connect_failures` |
| TUN trace | `epoch <n>: network change…`、`tunnel connect <addr> ok\|fail <proto> <ms>`、`tunnel closed <target> reason=…`，流结束原因增 `stall` |
| 应用日志 | `Connecting to server <name> (<addr>, tcp\|quic)`、`net change: default A -> B (原因)`、`DNS hijack enabled, …, tunnel AAAA = …` |
| CLI | `phantom client --tun-trace <path>` / `PHANTOM_TUN_TRACE`（Mac 用同一套分析器） |
| 鸿蒙偏好 | `phantom_ui.transport = tcp|quic`（默认 tcp，重启生效） |

### 验收阈值

弱网台架档位（固定，不再临时定义）：

| 档位 | 单向时延 | 丢包 | 限速 | 额外 |
|---|---|---|---|---|
| `W1` 通勤抖动 | 40 ms | 1% | 10 Mbit/s | — |
| `W2` 弱信号 | 100 ms | 3% | 2 Mbit/s | — |
| `W3` 过隧道断流 | 75 ms | 5% | 4 Mbit/s | 每 40 s 断流 8 s |

- 鸿蒙 TUN 平均下行 ≥ 同档 SOCKS5 传输参照的 **60%**，且 ≥ 同档 Mac 桌面 TUN 参照的 **80%**；
- 内层重传 ≤ **5 次/分钟**、重复注入 ≤ **1.2×** 有效字节；外层内核重传首轮只报告
  （W1/W2 目标 ≤3%、W3 ≤8%，基线出来后校准）；
- `W3` 每次断流结束后 **5 s 内**下行恢复到断流前的 ≥50%，整段 `flow_stall_drops = 0`、
  `vpn-tun` TX dropped 增量为 0；
- 不回归：WiFi 两工况复跑 `PERF_TUN_PATH_REPORT.md` 的阈值（视频 ≥250 KB/s、
  `dl.google.com` ≥12 MB、重传 ≤5/分钟、TX dropped=0）；Mac loopback 与 VPS 中位相对基线
  下降 ≤5%、`--check-unblock` 全绿。

### 验证

- 单测：`cargo test -p phantom-client --lib` 90 passed（含 30 s 放弃 + RST + relay 释放、
  IPv6 缓存/应答、单服务器重置只触发一次）；`cargo test -p phantom-e2e --release` 全绿
  （含 `weak_network`、`tcp_session_pool`、`quic_mux`）。
- 真机（蜂窝）：修复前 `2404:6800:4005:827::200e` 的 `SYN_SENT` 挂在运营商地址 25 s+ 且
  日志无 `ipv6`；第一次修复后源地址变成 `fd00:8:8::2`，但 **google.com 仍打不开**
  （App 反复重试 IPv6）；补上 W5b 后 google.com 与 m.youtube.com 均完整加载。
- 传输：VPS 上 TCP 443 与 UDP 443 同时监听；Mac CLI 以 `proto=quic` 与 `proto=tcp` 分别
  访问 `google/generate_204` 均 204（0.28 s / 0.26 s）；手机侧补验到
  `Connecting … , quic)` → `Tunnel established`（QUIC 会话真的建起来了），验完切回 TCP。
- Mac 不回归：`--loopback` 中位 1104 MB/s（基线 930–1016）；`--origin vps` 隧道 0.35 MB/s
  vs 同轮裸链路 0.34 MB/s，`--check-unblock` 全绿（204/204/200 + HKG）。
- 待补：`W1/W2/W3 × {下载, 播放}` 的台架 A/B、WiFi 两工况回归、Mac speedtest 三档，
  见 `tests/PERF_WEAKNET_REPORT.md`。

### 明确不做

- 地铁真机复核（用户确认无法执行）；台架只复现路径劣化，不覆盖射频层。
- 内层拥塞控制（无损本机路径，没有拥塞可测）；自研 BBRv2/v3/Copa/PCC。

### 假设与默认

- 默认传输保持 **TCP**；QUIC 只作为开关与 A/B 候选，是否改默认由 `PERF_WEAKNET_REPORT.md`
  的数据决定。
- 服务端可改（本轮只加了一个并跑的 QUIC 实例，不动协议）；不做历史协议兼容，三端同步升级。
- 弱网台架复现的是**路径劣化**（时延/丢包/限速/断流），不覆盖射频层（RRC 状态迁移、上行
  调度）；台架要求手机与 Mac 在同一 LAN，收工必须 `weaknet-mac.sh teardown`。
- 若 macOS pf 与用户既有代理/VPN 软件冲突，回退顺序：VPS 侧 `tc netem` → 仓库内
  `lossy_proxy`（QUIC 真丢包、TCP 仅时延）。
- 不提交密钥与真实服务器地址；台架用的临时链接（指向 Mac IP）只存在于手机本地。
- 窗口缩放 wscale：按证据触发，触发条件写在 `tests/PERF_WEAKNET_REPORT.md`。
- 服务端 IPv6 出口（当前 VPS 无 IPv6，隧道内 IPv6 目标快速失败回落 IPv4）。
